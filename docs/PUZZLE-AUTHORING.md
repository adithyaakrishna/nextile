# Puzzle authoring

Every puzzle is written from a rule, generated by the engine, checked by a solver that looks for other readings a player might see, and reviewed before it is scheduled. This is the workflow.

## 1. Write the rule

Create `src/content/puzzles/p-NNNN.ts` with the next unused number. IDs are never reused. Leave `sequence`, `choices` and `explanation` empty.

```ts
import { cycle, definePuzzle, parallel } from "../define";

export default definePuzzle({
  id: "p-0066",
  family: "two-clocks",
  difficulty: "easy", // overwritten with the computed tier by puzzle:build
  shown: 4,
  rule: parallel({
    base: { fill: "solid", count: 1 },
    vary: { color: cycle("pink", "blue"), shape: cycle("circle", "square", "triangle") },
  }),
  sequence: [],
  choices: [],
  answerIndex: 0,
  explanation: "",
  review: null,
});
```

Anything not listed under `vary` is a constant taken from `base` or the defaults (one blue solid circle at the center, rotation 0).

### Rule helpers

| Helper | Produces | Example |
|---|---|---|
| `cycle(a, b, c)` | a b c a b c … | `cycle("pink", "blue")` |
| `step(track, start, by)` | walks an ordered track, wrapping | `step("rotation", 0)`, `step("count", 3, -1)`, `step("corners", 0)` |
| `bounce(a, b, c)` | a b c b a b c … | `bounce(1, 2, 3)` |
| `stutter(hold, a, b, c)` | a a b b c c … | `stutter(2, "circle", "square", "triangle")` |
| `interleave(first, second)` | two sequences take turns | see `p-0026` |

Tracks: `rotation` (0, 90, 180, 270), `count` (1, 2, 3), and for position `corners` (clockwise), `ring` (every edge cell, clockwise), `rowMajor` (reading order), `middleRow`, `middleColumn`.

An "odometer" (one property moves on only when another starts over) is a `stutter` whose `hold` equals the other property's period. See `p-0027`, `p-0028`, `p-0030` and `p-0064`.

### Things the validator will reject

- **Invisible changes.** A solid circle, square or diamond looks the same at every rotation, and a striped one looks the same at 0° and 180°. Rotate triangles, or use `cycle(0, 90)` on striped shapes. Every tile must already be in canonical form.
- **Position with more than one symbol.** Position only exists when every tile has a count of 1.
- **Not enough evidence.** Steps need two visible transitions; a cycle of length p needs p + 1 tiles; a stutter needs one complete run. A four-tile stutter like ● ● ■ ■ can't tell the player what follows the squares, so show five tiles.

## 2. Build it

```sh
pnpm puzzle:build p-0066
```

This fills in the sequence from the rule, writes the computed difficulty, proposes distractors and picks three, places the answer, and drafts an explanation. It prints a preview, the difficulty points, the other distractor candidates, and the result of every per-puzzle check. Re-run with `--force` to re-pick distractors, `--explain` to redraft the explanation, or `--answer=3` to put the answer in a given slot.

Distractor recipes, in order of preference: **phase slip** (a cycling property one position off), **over-step** (moved two instead of one), **wrong stream** (the other interleaved sequence's next tile), **early wrap** (a bounce or stutter turning early), **repeat last** (assumed nothing changed), **tweak** (another value of a changing property), and **decoy** (a property that never changes, used only when nothing better exists). Each distractor must differ from the answer in one or two properties, and none may be predicted by any reading the solver finds.

## 3. Look at it

```sh
pnpm puzzle:preview p-0066   # ASCII in the terminal, plus tmp/contact-sheet.svg
pnpm dev                     # then open /dev/puzzles for every puzzle at real size on both mats
```

## 4. Solve it cold and review it

A person who hasn't seen the rule solves it with a timer, edits the explanation for voice, and fills in `review`:

```ts
review: { by: "initials", on: "2026-11-02" },
```

Explanations are one or two sentences, at most 180 characters. The part before "Next is" must mention every property that changes and must not use the generic word for one that doesn't (for example, don't say "colors" in a puzzle where every tile is pink). Avoid "turns" unless rotation changes, so write "alternate" rather than "take turns".

**Current state:** all 65 puzzles carry `review: { by: "ai-agent", … }`. That records an AI agent's review of the sequence, choices and wording, not a person's cold solve. `pnpm validate:puzzles` lists them as needing a human review; replace each with a person's initials once they have solved it.

## 5. Validate

```sh
pnpm validate:puzzles
```

Runs all twelve publication checks over the whole collection and schedule: the sequence matches the rule, the answer matches, the solver predicts exactly one choice and it passes the Occam check, the choices are distinct, every tile is canonical, position rules, distractor distance, explanation keywords and length, computed difficulty, no duplicates in disguise, review present, and published puzzles unchanged. It also checks the schedule starts on launch day with no gaps or repeats, that answer positions are each used 20–30% of the time and never three days running, and that at least 7 days of runway remain (14 for no warning). `pnpm build` runs it first and fails on any error.

## 6. Schedule

```sh
pnpm schedule:extend          # every reviewed, valid puzzle not yet scheduled
pnpm schedule:extend --days=7 # or just the next week
```

Appends days after the last scheduled one in the weekly rhythm (easy Monday and Tuesday, medium Wednesday to Friday and Sunday, hard Saturday), avoiding the same family two days running, and moves each puzzle's answer to keep positions balanced. Past dates are never touched.

## 7. Freeze

Once a puzzle's day arrives it must never change, because shared results point at it. `pnpm lock:published` (run daily or on every deploy) writes a SHA-256 of each published puzzle's sequence, choices and answer into `src/content/published.lock.json`. Validation fails if a locked puzzle or its day in the schedule changes. Future puzzles stay editable.
